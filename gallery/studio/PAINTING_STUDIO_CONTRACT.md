# 绒球水墨画房 · Ink Painting Studio v1.0

> 本文件是绒球**使用水墨工具进行艺术创作**的生产契约。
> 与「水墨工坊」（STUDIO_CONTRACT.md，工具制造）并列，构成双环：
> **画房作画 → 发现工具不够 → 工坊改工具 → 画房作出更好的画。**
>
> 画房的判据不是"代码对不对"，而是"画好不好看"。

---

## 1. 画房边界

画房是**创作容器**，拥有：创作流程、审美判据、迭代纪律、作品档案。
它**不拥有**：工具代码、生成器算法、Agent身份。

```
画房 uses → 工坊产出的工具（Ink Builder、墨园等）
画房 feeds back → 工坊的工具缺陷与需求
```

画房关心的问题：
- 这幅画能不能挂出来？
- 叶子交叉的位置对不对？
- 留白够不够、气通不通？
- 花是不是像污点不像花？
- 这一版比上一版好在哪、坏在哪？

画房**不**关心的问题（交给工坊）：
- 悬臂梁积分有没有bug
- brush stamp的opacity叠加是否正确
- CDP截图为什么超时

## 2. 核心原则

### 2.1 先看真迹，再动笔

动手调参之前，必须先看3-5幅同题材的经典名作（宋/元/明/清），不是为了抄，而是为了建立**视觉参照系**。

不凭想象调参。"我觉得兰花应该长这样"和"赵孟坚的兰花确实是这样"是两件事。

研究方法：
- 搜索名家真迹（赵孟坚、文徵明、郑思肖、石涛、八大山人……按题材选）
- 观察三件事：①元素怎么排布（构图）②线条怎么走（笔法）③哪里有、哪里没有（取舍）
- 用一句话写下最关键的发现，作为这一轮创作的视觉锚点

### 2.2 每轮只改一个致命问题

看到一张不满意的图，会同时发现很多问题。但每轮只选**最致命的一个**改，其他记下来排队。

理由：同时改五个变量，下一轮无法判断哪个改动有效、哪个有害。九轮幽兰的经验是——叶数、叶基宽度、角度、弯度、花位置，如果同时调，根本分不清因果。

改完立即出图验证，再看下一个问题。

### 2.3 不选彩票，要作画

跑100张随机种子挑一张，不是创作，是买彩票。

创作是**主动决定**：
- 叶基放在画面的哪个位置
- 哪片叶长、哪片短
- 哪片挺拔、哪片弯垂
- 花在哪里开
- 画面的哪个区域必须留空

随机种子可以用来探索可能性，但最终作品必须经过手动构图和取舍。compose模式存在的意义就是让创作者能指定这些。

### 2.4 七分为人，三分为己

- **7分门槛**：自评低于7分的作品不给主人看，也不上线画廊。7分的标准是"第一眼不需要解释，就像一幅能挂在画廊的水墨小品"。
- **诚实自评**：好就是好，不好就是不好。不拔高分数，也不过度自贬。自评必须同时写"得"和"失"。
- **过了7分就停**：不要无限打磨。8分以上的改进是边际收益递减，而且可能伤了作品的生气。7.2分的幽兰可以上线，不需要磨到9分。

### 2.5 不手补原则（创作版）

生成出来的画有缺陷，如果是**工具/算法层面**的问题（如线条太数学、花色偏灰），改工具参数或回流给工坊，不用图片编辑软件在成品上修。

如果是**构图/选择层面**的问题（如叶子位置不好、花太多），调整构图参数重新生成。

成品PNG是最终产物，不在上面PS。

### 2.6 工具缺陷必须回流

创作中发现的工具层问题，不能只是"这版先忍了"。每条都记录，回流给工坊：

| 创作中发现的问题 | 路由 |
|---|---|
| 叶子位置偏左30px | 画房调构图 |
| 花太小看不见 | 画房调fsz参数 |
| 所有叶子弯垂曲线一模一样 | **工坊：悬臂梁需引入顿挫/飞白** |
| 花瓣在宣纸上发灰 | **工坊：花色渲染/透明度需改进** |
| CDP截图偶尔超时 | **工坊：截图脚本bug** |

判断标准：**改构图/参数能解决的→画房；改算法/引擎才能解决的→工坊。**

## 3. 角色

画房是轻量创作模式，绒球单Agent可独立完成全部环节。复杂作品可派sub-agent协作。

| 角色 | 职责 | 由谁担任 |
|------|------|----------|
| **画家（Maker）** | 研、作、磨，实际产出作品 | 主会话绒球 / codeact sub-agent |
| **观者（Viewer）** | 看完图给第一印象，不看代码、不看参数，只说"我看到什么、感觉如何" | 主会话绒球（切换视角）/ lead sub-agent |
| **评者（Critic）** | 对照审美标准逐条诊断，标出最致命的问题 | 主会话绒球 / lead sub-agent |
| **记录者（Archivist）** | 保存参数档案、得失记录、迭代日志 | 主会话绒球 |

**画家不评自己的画。** 每轮出图后，先以观者身份看（不看代码），再以评者身份诊断。两种视角的感受分开记录。

> 攻墨（众审循环）复用工坊契约5.4的机制，画房可按需调用。
> 创作类作品的攻墨视角侧重：构图、气韵、笔墨、留白、立意，而非代码质量。

## 4. 创作流程

### 4.1 研（Research）

- **触发**：有了创作念头（"想画一丛兰""想画风中的竹"）
- **做什么**：
  1. 看3-5幅同题材真迹，写下视觉锚点
  2. 明确这幅画的"一句话意图"：不是"画兰花"，而是"空谷里一丛开着花的兰，大部分纸是空的"
  3. 确认用什么工具、什么模式（墨园compose？即梦？手写Canvas？）
- **产出**：一段简短的创作笔记（意图+锚点+工具选择），存入 `process/作品名/`

### 4.2 作（Draft）

- **做什么**：
  1. 快速出第一版，不追求一次成
  2. 用compose模式或手动构图，主动决定主要元素位置
  3. 出图后**先以观者身份看**：不放大、不看代码、不读参数，第一眼感觉是什么
- **产出**：第一版截图 + 观者第一印象笔记

### 4.3 诊（Diagnose）

- **做什么**：
  1. 切换到评者视角，列出所有问题
  2. 选**最致命的一个**作为下一轮目标
  3. 判断问题路由：画房调参可解决？还是工坊工具缺陷？
  4. 工坊缺陷记入 `feedback/`，不阻塞当前创作（除非致命到无法继续）
- **产出**：诊断笔记（问题排序 + 本轮只改什么 + 路由判断）

### 4.4 磨（Iterate）

- **做什么**：
  1. 只改诊断选中的那一个问题
  2. 重新出图
  3. 观者看 → 评者诊 → 选下一个致命问题
  4. 重复4.2-4.4循环
- **纪律**：
  - 每轮截图保存到 `process/作品名/v{N}/`
  - 每轮写一句话：这轮改了什么、效果如何
  - 不要在一轮里同时改叶数+角度+花色+构图

### 4.5 裁（Verdict）

- **什么时候停**：
  - 自评达到7分（"第一眼不需要解释就像一幅画"）
  - 或连续两轮改进不明显，开始进入"过度打磨"
  - 或再改会伤害已经成立的部分
- **做什么**：
  1. 从所有版本中选最终作品（不一定是最后一版）
  2. 写自评：得（3-5条）、失（2-4条）、分数（1-10）
  3. 记录参数档案（关键参数值，供下一幅同类作品参考）
- **产出**：作品笔记 `.md` + 最终作品 `.png`

### 4.6 馈（Feedback）

- **做什么**：
  1. 整理 `feedback/` 中积累的工具缺陷
  2. 按严重程度排序，提交给工坊作为下一轮工具改进的需求
  3. 更新画房自身的经验（如"兰花叶基必须宽幅错开"这类可复用知识写入第6节）
- **产出**：工具需求清单 + 本契约更新

## 6. 创作经验库（从真实作品中积累）

### 6.1 折枝花卉通用

- **折枝模式需要独立参数集**：花园模式植物贴地（叶短基窄），折枝模式需要叶长1.5-1.8倍、基宽25-30px、弯度更大。两种模式不能共用一套参数。
- **叶基宽幅错开是中段交叉的关键**：叶基只在6-10px错开时，叶子在根部就挤成一团；拉宽到28px后，叶子从不同位置出发，在画面中段才交汇形成凤眼。
- **sag必须克制且有层次**：所有叶子同样弯度=对称喷泉=灾难。主叶挺拔（0.2-0.3）、交凤眼斜出（0.3-0.5）、破凤眼弯垂（0.6-0.8），形成直曲对比。
- **叶根不能用机械圆点**：ellipse在视觉上像标签/橄榄，要用沿叶反方向的短粗藏锋笔触。

### 6.2 兰花专项（来自《幽兰》九轮迭代）

- 叶数7-9片（宋画标准），不能只有4-5片
- 花色：主花淡墨alpha 0.65、辅花清墨alpha 0.50，花心胭脂alpha 0.70；花位置在叶上半段（t=0.28-0.53），不在叶尖
- 悬臂梁t²弯垂视觉上太光滑对称，缺少人手顿挫飞白——**已识别为工坊待改进项**
- 花瓣在宣纸上对比度不够，远看发灰——**已识别为工坊待改进项**
- 单丛兰在大面积留白中略单薄，但"空谷"之意也来自单丛，这是取舍不是缺陷

### 6.3 构图通用

- **折枝入画**：植物不必须贴在ground线上，可以从画面边缘或中下部入画
- **疏可走马，密不透风**：有叶子的地方密集交叉，没有叶子的地方大面积留白，不要均匀分布
- **不对称**：叶基偏一侧，长叶扫向另一侧，形成动势。居中=标本=死
- **先决定哪里不画**：留白区域要主动规划，不是"剩下的地方"

## 7. 画房与工坊的双环协议

```
                    ┌─────────────┐
                    │   画 房      │
                    │ （创作循环）  │
                    │ 研→作→诊→磨  │
                    └──────┬──────┘
                           │ 发现工具缺陷
                           ▼
                    ┌─────────────┐
                    │  feedback/   │
                    │  工具需求清单 │
                    └──────┬──────┘
                           │ 提交需求
                           ▼
                    ┌─────────────┐
                    │   工 坊      │
                    │ （开发循环）  │
                    │ Build→Test  │
                    │   →Fix      │
                    └──────┬──────┘
                           │ 新工具/改进
                           ▼
                    ┌─────────────┐
                    │  画房使用    │
                    │  作出更好的画 │
                    └─────────────┘
```

**规则**：
1. 画房不等工坊——工具不够用时，用现有工具做到最好，缺陷记录在案
2. 工坊不从零造功能——只做画房真正需要、且在feedback中有据可查的改进
3. 工坊的新模块必须经过画房使用验证，才能标记为"稳定"
4. 每次工坊升级工具后，画房应尝试用新工具重画或改进已有作品
